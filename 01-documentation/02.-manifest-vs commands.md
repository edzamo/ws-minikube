## Píldora 1: Ubicación y contenido de kubeconfig

### Ubicación del archivo de configuración

El archivo que define a qué clúster se conecta `kubectl` está en:

```sh
# En Linux/macOS
~/.kube/config

# Ruta absoluta típica (Linux)
/home/<usuario>/.kube/config

# Ver el contenido
cat ~/.kube/config
```

### Qué contiene el kubeconfig

Al ejecutar `cat ~/.kube/config` verás un YAML con varias secciones. Resumen de lo que significa cada parte:

| Sección | Qué contiene | Para qué sirve |
|--------|---------------|----------------|
| **clusters** | Lista de clústeres conocidos | Define *dónde* está el API de Kubernetes |
| **cluster.server** | URL del API (ej: `https://192.168.49.2:8443`) | **IP y puerto** del plano de control. Es la dirección a la que `kubectl` envía todas las peticiones. |
| **cluster.certificate-authority** | Ruta al archivo del certificado CA (ej: `~/.minikube/ca.crt`) | Certificado raíz para **verificar que el servidor es quien dice ser** (evitar suplantación). |
| **users** | Credenciales para autenticarse | Quién eres ante el clúster |
| **user.client-certificate** | Ruta al certificado del cliente | **Certificado** que identifica a tu usuario (ej: admin). |
| **user.client-key** | Ruta a la clave privada del cliente | **Clave privada** asociada al certificado. Nunca la compartas. |
| **contexts** | Combinación cluster + user + (opcional) namespace | Qué clúster y qué usuario usar en cada “contexto”. |
| **current-context** | Nombre del contexto activo | El contexto que está usando `kubectl` ahora (ej: `minikube`). |

### La IP en kubeconfig

- **cluster.server** es la URL del API server (incluye host y puerto).
- En Minikube, el host suele ser una IP como `192.168.49.2` (red interna del driver Docker/VM) y el puerto `8443`.
- Esa IP puede cambiar cada vez que reinicias Minikube; por eso `kubectl` lee siempre desde `~/.kube/config`, que Minikube actualiza al iniciar.

### Los certificados

- **CA (certificate-authority):** para confiar en el API server (conexión TLS).
- **client-certificate + client-key:** para que el API server sepa qué usuario eres (autenticación).
- Sin estos certificados y la clave, no podrías conectarte de forma segura al clúster.

## Píldora 2: Formas de crear recursos

Hay varias maneras de crear y modificar recursos en Kubernetes.

### 1. Forma declarativa (manifiestos)

Defines el **estado deseado** en un archivo YAML (o JSON) y Kubernetes se encarga de alcanzarlo.

- **Ventajas:** Versionable, repetible, documentado, idempotente.
- **Comando típico:** `kubectl apply -f archivo.yaml`

```sh
# Crear o actualizar recursos desde un archivo
kubectl apply -f deployment.yaml

# Desde un directorio (todos los YAML)
kubectl apply -f ./manifiestos/

# Ver qué se aplicaría sin hacer cambios
kubectl apply -f deployment.yaml --dry-run=client -o yaml
```

### 2. Forma imperativa

Creas o modificas recursos **con comandos** en la terminal, sin (o con poco) archivo YAML.

- **Ventajas:** Rápido para pruebas y comandos puntuales.
- **Desventajas:** Menos trazabilidad y más difícil de reproducir.

```sh
# Crear un deployment
kubectl create deployment nginx --image=nginx:latest --replicas=2

# Crear un pod
kubectl run mi-pod --image=nginx:latest

# Crear un servicio
kubectl create service clusterip mi-svc --tcp=80:80
```

### 3. Forma imperativa con archivo

Generas el YAML con un comando y luego lo aplicas o lo guardas.

```sh
# Generar YAML sin crear el recurso
kubectl create deployment nginx --image=nginx --dry-run=client -o yaml > deploy.yaml

# Editar y aplicar
kubectl apply -f deploy.yaml
```

### 4. Otras formas

| Forma | Descripción | Ejemplo |
|-------|-------------|--------|
| **Kustomize** | Parches y overlays sobre YAML base | `kubectl apply -k ./overlays/prod` |
| **Helm** | Plantillas y paquetes (charts) | `helm install mi-app ./chart` |
| **Edit directo** | Editar el recurso en el clúster | `kubectl edit deployment nginx` |
| **API directa** | Llamadas HTTP al API server | Uso desde programas o scripts |

### Cuándo usar cada una

- **Manifiestos (declarativa):** entornos estables, CI/CD, equipo, todo lo que quieras versionar.
- **Imperativa:** pruebas rápidas, limpieza (`kubectl delete`), comandos únicos.
- **Kustomize/Helm:** cuando necesitas reutilizar el mismo diseño con distintos entornos o valores.

## Píldora 3: Estructura de un manifiesto

### Taxonomía general

Casi todos los recursos siguen esta estructura:

```yaml
apiVersion: ...    # Versión del API de Kubernetes
kind: ...          # Tipo de objeto
metadata: ...      # Identificación y etiquetas
spec: ...          # Estado deseado (qué quieres)
status: ...        # Estado actual (lo rellena Kubernetes, no sueles escribirlo)
```

### Tipos de objetos (kind) más comunes

| kind | Qué representa |
|------|-----------------|
| **Pod** | Una o más contenedores que se ejecutan juntos. |
| **Service** | Punto de acceso estable a uno o más pods (IP estable, puerto). |
| **Deployment** | Gestión de pods con actualizaciones y réplicas. |
| **ReplicaSet** | Mantiene un número fijo de réplicas de pods (lo usa Deployment). |
| **ConfigMap** | Configuración en pares clave-valor. |
| **Secret** | Datos sensibles (contraseñas, tokens). |
| **Namespace** | Agrupación lógica de recursos. |
| **Ingress** | Reglas de entrada HTTP/HTTPS desde fuera del clúster. |

### apiVersion

Indica la versión del recurso en el API:

- **v1:** Pod, Service, ConfigMap, Secret, Namespace, etc.
- **apps/v1:** Deployment, ReplicaSet, StatefulSet.
- **networking.k8s.io/v1:** Ingress, NetworkPolicy.
- **batch/v1:** Job, CronJob.

### metadata

Identificación y etiquetas del recurso:

```yaml
metadata:
  name: mi-deployment          # Nombre único en el namespace
  namespace: default            # Namespace (opcional, default = default)
  labels:
    app: nginx
    env: prod
  annotations:
    descripcion: "Deployment de ejemplo"
```

- **name:** nombre del recurso (obligatorio en la mayoría).
- **namespace:** dónde vive el recurso.
- **labels:** para seleccionar recursos (selectors, `kubectl -l app=nginx`).
- **annotations:** información extra no usada por Kubernetes para selección.

### spec

Define el **estado deseado** del recurso. Cada `kind` tiene su propio `spec`.

**Ejemplo Pod:**

```yaml
spec:
  containers:
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80
```

**Ejemplo Deployment:**

```yaml
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:          # Plantilla para crear los Pods
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
```

### status

Kubernetes rellena **status** con el estado actual (condiciones, IPs, etc.). No lo defines tú en el manifiesto; es solo lectura en la práctica.

## Píldora 4: Comandos kubectl más usados

### kubectl get all

Muestra de un vistazo los recursos principales del namespace actual: pods, services, deployments, replicasets.

```sh
kubectl get all
```

**Salida típica:**

```
NAME                           READY   STATUS    RESTARTS   AGE
pod/nginx-7c45b84548-abc12      1/1     Running   0          5m

NAME                 TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
service/kubernetes   ClusterIP   10.96.0.1       <none>        443/TCP   1d
service/nginx        ClusterIP   10.96.1.10      <none>        80/TCP    5m

NAME                    READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/nginx   1/1     1            1           5m

NAME                               DESIRED   CURRENT   READY   AGE
replicaset.apps/nginx-7c45b84548    1         1         1       5m
```

### Tabla de comandos más usados

| Comando | Qué hace |
|---------|----------|
| **`kubectl get all`** | Lista pods, services, deployments y replicasets del namespace actual. |
| **`kubectl get pods`** | Lista pods. |
| **`kubectl get pods -o wide`** | Lista pods con más datos (IP del pod, nodo). |
| **`kubectl get pods -A`** o **`kubectl get pods --all-namespaces`** | Lista pods de todos los namespaces. |
| **`kubectl get svc`** | Lista servicios. |
| **`kubectl get deploy`** | Lista deployments. |
| **`kubectl get nodes`** | Lista nodos del clúster. |
| **`kubectl describe pod <nombre>`** | Detalle de un pod (eventos, condiciones, contenedores). |
| **`kubectl describe svc <nombre>`** | Detalle de un servicio (endpoints, selector). |
| **`kubectl logs <pod>`** | Logs del pod. |
| **`kubectl logs -f <pod>`** | Logs en tiempo real (follow). |
| **`kubectl apply -f archivo.yaml`** | Crear o actualizar recursos desde un manifiesto. |
| **`kubectl delete -f archivo.yaml`** | Eliminar los recursos definidos en el archivo. |
| **`kubectl delete pod <nombre>`** | Eliminar un pod (el controller puede recrearlo si hay Deployment/ReplicaSet). |
| **`kubectl delete deploy <nombre>`** | Eliminar un deployment (y sus pods). |
| **`kubectl exec -it <pod> -- /bin/sh`** | Abrir shell en el contenedor del pod. |
| **`kubectl config use-context <contexto>`** | Cambiar el contexto (clúster/usuario) activo. |
| **`kubectl config current-context`** | Ver el contexto actual. |

### Opciones útiles con get

```sh
# Formato de salida
kubectl get pods -o yaml
kubectl get pods -o json
kubectl get pods -o wide

# Filtrar por etiqueta
kubectl get pods -l app=nginx

# Ver todos los namespaces
kubectl get pods -A

# Namespace concreto
kubectl get pods -n kube-system

# Watch (actualización continua)
kubectl get pods -w
```

## Píldora 5: Servicios

### Qué es un Service

Un **Service** es un objeto que define una forma estable de acceder a un conjunto de pods (normalmente por etiquetas). Proporciona:

- Una **IP estable** (ClusterIP) dentro del clúster.
- Un **nombre DNS** (ej: `mi-servicio.default.svc.cluster.local`).
- **Balanceo de carga** entre los pods que coinciden con el selector.

Los pods pueden nacer y morir; el Service sigue apuntando a los que cumplan las etiquetas.

### Tipos de Service

| Tipo | Uso | Acceso |
|------|-----|--------|
| **ClusterIP** | Uso interno en el clúster | Solo desde dentro del clúster (por defecto). |
| **NodePort** | Exponer en un puerto de cada nodo | `<NodoIP>:<NodePort>`. |
| **LoadBalancer** | IP externa (cloud o Minikube tunnel) | Tráfico externo. |
| **ExternalName** | Alias a un nombre DNS externo | Resolución DNS. |

### Estructura mínima de un Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: mi-servicio
spec:
  selector:
    app: nginx       # Debe coincidir con labels de los Pods
  ports:
    - port: 80      # Puerto del Service
      targetPort: 80  # Puerto del contenedor en el Pod
  type: ClusterIP   # opcional; ClusterIP es el valor por defecto
```

### Ejemplos de Services

**1. Service ClusterIP (interno):**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api-backend
spec:
  selector:
    app: api
  ports:
    - port: 8080
      targetPort: 8080
  type: ClusterIP
```

**2. Service NodePort (acceso desde fuera por puerto del nodo):**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-nodeport
spec:
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080   # Puerto en cada nodo (rango 30000-32767)
  type: NodePort
```

**3. Service para un Deployment:**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web    # Mismo label que el Deployment pone a sus Pods
  ports:
    - port: 80
      targetPort: 8080
```

### Comandos útiles con Services

```sh
kubectl get svc
kubectl describe svc mi-servicio
kubectl get endpoints mi-servicio   # Pods detrás del Service
```

## Píldora 6: Deployments y ReplicaSets

### Qué es un Deployment

Un **Deployment** es un controlador de alto nivel que:

- Mantiene un número **deseado de réplicas** de pods.
- Gestiona **actualizaciones** (rolling update, rollback).
- Crea y gestiona **ReplicaSets** por debajo.

No creas pods sueltos en producción; creas un Deployment y él crea los pods.

### Qué es un ReplicaSet

Un **ReplicaSet** mantiene un número fijo de pods que coinciden con un selector de etiquetas. Si un pod se cae, el ReplicaSet crea otro.

- **Deployment** = “quiero N réplicas de esta plantilla y quiero poder actualizarlas”.
- **ReplicaSet** = “mantén exactamente N pods con estas etiquetas”.

En la práctica sueles trabajar con **Deployments**; los ReplicaSets se crean automáticamente.

### Cuándo usar cada uno

| Objeto | Cuándo usarlo |
|--------|----------------|
| **Deployment** | Casi siempre: apps web, APIs, workers que escalan y se actualizan. |
| **ReplicaSet** | Raramente directo; lo usa el Deployment. Solo si necesitas un control muy simple sin actualizaciones. |
| **Pod solo** | Pruebas puntuales, troubleshooting, jobs de una sola ejecución. |

### Estructura de un Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.24
          ports:
            - containerPort: 80
```

- **replicas:** cuántos pods quieres.
- **selector:** qué pods “posee” este Deployment (por labels).
- **template:** la plantilla con la que se crean los pods (metadata + spec de Pod).

### Ejemplo completo: Deployment + Service

**deployment.yaml:**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
```

**service.yaml:**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx
spec:
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80
  type: ClusterIP
```

**Aplicar:**

```sh
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml

# Ver todo junto
kubectl get all
```

### Comandos útiles con Deployments

```sh
# Escalar
kubectl scale deployment nginx --replicas=5

# Ver el ReplicaSet creado por el Deployment
kubectl get rs

# Historial de versiones
kubectl rollout history deployment nginx

# Rollback
kubectl rollout undo deployment nginx

# Estado del rollout
kubectl rollout status deployment nginx
```

## Resumen rápido

| Tema | Punto clave |
|------|-------------|
| **kubeconfig** | `~/.kube/config`: IP del API (server), certificados (CA, client), contexto activo. |
| **Crear recursos** | Declarativa (manifiestos), imperativa (comandos), Kustomize/Helm. |
| **Manifiesto** | apiVersion, kind, metadata (name, labels), spec; status lo rellena Kubernetes. |
| **Comandos** | `kubectl get all`, `get pods`, `get svc`, `describe`, `logs`, `apply -f`, `delete`. |
| **Service** | IP estable, DNS, balanceo; tipos: ClusterIP, NodePort, LoadBalancer. |
| **Deployment** | Réplicas + actualizaciones; usa ReplicaSet por debajo. Usar Deployment para apps; Pod solo para pruebas. |
