## Píldora 1: ¿Qué es un Pod? Diferencia con contenedor

### ¿Qué es un Pod?

Un **Pod** es la **unidad más pequeña y básica** que se puede desplegar y gestionar en Kubernetes. Representa una instancia en ejecución de uno o varios contenedores que comparten recursos.

### Diferencia entre Pod y contenedor

| Concepto | Descripción |
|----------|-------------|
| **Contenedor** | Un proceso aislado que ejecuta una aplicación (ej: Docker container). Es la unidad técnica de ejecución. |
| **Pod** | Un "envoltorio" de Kubernetes que contiene uno o más contenedores. Es la unidad lógica que Kubernetes gestiona. |

**Analogía:**
- **Contenedor** = el motor de un coche
- **Pod** = el coche completo (motor + chasis + sistema eléctrico)

### Características principales de un Pod

1. **Uno o varios contenedores:** Normalmente un Pod tiene un solo contenedor, pero puede tener varios que necesiten trabajar juntos.

2. **Red compartida:** Todos los contenedores de un Pod comparten:
   - La misma dirección IP
   - El mismo espacio de nombres de red
   - Pueden comunicarse vía `localhost`

3. **Almacenamiento compartido:** Los contenedores pueden acceder a volúmenes compartidos definidos en el Pod.

4. **Ciclo de vida conjunto:** Los contenedores de un Pod se crean, inician, detienen y eliminan juntos.

### ¿Por qué Pods y no contenedores directamente?

Kubernetes gestiona Pods (no contenedores directamente) porque:

- **Abstracción:** Permite agrupar contenedores relacionados que deben trabajar juntos.
- **Gestión:** Kubernetes puede planificar, monitorear y gestionar el ciclo de vida de manera uniforme.
- **Recursos:** Permite definir límites de recursos (CPU, memoria) a nivel de Pod.

### Ejemplo visual

```
Pod "mi-app"
├── Contenedor: nginx (puerto 80)
└── Contenedor: sidecar-logger (comparte red y volúmenes)
```

**En la práctica:** La mayoría de los Pods tienen un solo contenedor. Los Pods multi-contenedor se usan para casos especiales como sidecars o helpers.

## Píldora 2: Taxonomía básica de un Pod

### Estructura básica de un manifiesto Pod

```yaml
apiVersion: v1          # Versión del API (v1 para Pods)
kind: Pod               # Tipo de recurso
metadata:               # Información de identificación
  name: mi-pod          # Nombre único del Pod
  labels:               # Etiquetas para selección
    app: nginx
spec:                   # Especificación del Pod
  containers:          # Lista de contenedores
    - name: nginx
      image: nginx:latest
```

### Componentes principales

#### apiVersion

- Para Pods siempre es **`v1`**
- Indica qué versión del API de Kubernetes usar

#### kind

- Siempre **`Pod`** para este tipo de recurso
- Indica el tipo de objeto que estás creando

#### metadata

Información sobre el Pod:

```yaml
metadata:
  name: mi-pod                    # Nombre único (obligatorio)
  namespace: default              # Namespace (opcional, default = default)
  labels:                         # Etiquetas para selección
    app: nginx
    env: production
  annotations:                    # Metadatos adicionales
    descripcion: "Pod de ejemplo"
```

- **name:** Identificador único del Pod en el namespace
- **namespace:** Dónde vive el Pod (por defecto: `default`)
- **labels:** Pares clave-valor para seleccionar y agrupar Pods
- **annotations:** Información adicional (no se usa para selección)

#### spec

Define el estado deseado del Pod:

```yaml
spec:
  containers:                    # Lista de contenedores (obligatorio)
    - name: nginx                # Nombre del contenedor
      image: nginx:latest        # Imagen Docker (obligatorio)
      ports:                     # Puertos expuestos
        - containerPort: 80
      resources:                 # Límites de recursos
        requests:
          memory: "64Mi"
          cpu: "250m"
        limits:
          memory: "128Mi"
          cpu: "500m"
  restartPolicy: Always          # Política de reinicio
```

**Campos importantes de spec:**

- **containers:** Lista de contenedores (al menos uno)
- **restartPolicy:** Qué hacer si el contenedor falla (`Always`, `OnFailure`, `Never`)
- **volumes:** Volúmenes compartidos entre contenedores (opcional)

### Ejemplo completo

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
    version: "1.0"
spec:
  containers:
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80
          name: http
      resources:
        requests:
          memory: "128Mi"
          cpu: "100m"
        limits:
          memory: "256Mi"
          cpu: "200m"
  restartPolicy: Always
```

## Píldora 3: Ciclo de vida de un Pod

### Estados de un Pod

Un Pod pasa por diferentes estados durante su vida:

| Estado | Descripción |
|--------|-------------|
| **Pending** | El Pod ha sido aceptado pero los contenedores aún no se han creado. Puede estar esperando recursos o descargando imágenes. |
| **Running** | El Pod está en un nodo y todos los contenedores están ejecutándose. |
| **Succeeded** | Todos los contenedores terminaron exitosamente (para Pods que ejecutan tareas de una sola vez). |
| **Failed** | Al menos un contenedor falló (terminó con error o fue terminado por el sistema). |
| **Unknown** | El estado del Pod no se pudo obtener (problema de comunicación con el nodo). |

### Fases del ciclo de vida

```
1. Creación del Pod
   ↓
2. Pendiente (Pending) - Esperando ser programado
   ↓
3. Programado (Scheduled) - Asignado a un nodo
   ↓
4. Inicialización (Init Containers si existen)
   ↓
5. Creación de contenedores
   ↓
6. Descarga de imágenes (Pull Image)
   ↓
7. Inicio de contenedores
   ↓
8. Running / Succeeded / Failed
```

### Comandos para ver el estado

```sh
# Ver estado de los Pods
kubectl get pods

# Ver detalles del estado
kubectl describe pod <nombre-pod>

# Ver eventos relacionados con el Pod
kubectl get events --field-selector involvedObject.name=<nombre-pod>
```

### Condiciones del Pod

Los Pods tienen condiciones que indican su estado:

- **PodScheduled:** El Pod ha sido programado en un nodo
- **Initialized:** Los contenedores init han terminado
- **ContainersReady:** Todos los contenedores están listos
- **Ready:** El Pod está listo para recibir tráfico

```sh
# Ver condiciones de un Pod
kubectl get pod <nombre-pod> -o yaml | grep -A 10 conditions
```

## Píldora 4: Tipos de procesos y políticas de reinicio

### Tipos de procesos según duración

| Tipo | Descripción | Ejemplo | restartPolicy recomendada |
|------|-------------|---------|---------------------------|
| **Proceso de larga duración** | Servicios que deben estar siempre corriendo (web servers, APIs, bases de datos) | nginx, API REST | `Always` |
| **Tarea de una sola vez** | Scripts o trabajos que se ejecutan una vez y terminan | Migración de BD, backup | `Never` o `OnFailure` |
| **Tarea periódica** | Trabajos que se ejecutan en intervalos (usar CronJob) | Reportes diarios | `Never` |

### restartPolicy

Define qué hacer cuando un contenedor termina:

| Valor | Qué hace |
|-------|----------|
| **Always** | Siempre reinicia el contenedor si termina (por defecto). Ideal para servicios que deben estar siempre corriendo. |
| **OnFailure** | Solo reinicia si el contenedor termina con código de error (no 0). Útil para trabajos que pueden fallar. |
| **Never** | Nunca reinicia el contenedor. Útil para trabajos de una sola ejecución. |

### Ejemplos según el tipo de proceso

**1. Servicio web (siempre corriendo):**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-server
spec:
  containers:
    - name: nginx
      image: nginx:latest
  restartPolicy: Always    # Se reinicia automáticamente si falla
```

**2. Tarea de una sola vez (migración):**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: db-migration
spec:
  containers:
    - name: migrate
      image: myapp:migrate
      command: ["/bin/sh", "-c", "python migrate.py"]
  restartPolicy: Never     # No se reinicia, solo se ejecuta una vez
```

**3. Tarea que puede fallar (backup):**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: backup
spec:
  containers:
    - name: backup-script
      image: backup:latest
  restartPolicy: OnFailure  # Solo se reinicia si falla
```

### Nota importante sobre Pods

**Los Pods NO se auto-reparan si se eliminan.** Si un Pod se elimina (accidentalmente o por fallo del nodo), **no se recrea automáticamente** a menos que esté gestionado por un controlador como:

- **Deployment:** Mantiene Pods corriendo y los recrea si se eliminan
- **ReplicaSet:** Mantiene un número fijo de réplicas
- **StatefulSet:** Para aplicaciones con estado
- **DaemonSet:** Un Pod por nodo

**Por eso:** En producción, usa **Deployments** en lugar de Pods directos.

## Píldora 5: Kubernetes Scheduler

### ¿Qué es el Scheduler?

El **Kubernetes Scheduler** es un componente del plano de control que decide **en qué nodo** se ejecutará cada Pod.

### ¿Dónde se crea el Pod?

**El Pod NO se crea directamente en un nodo.** El proceso es:

1. **Usuario/Controlador** crea el Pod → Se guarda en el API Server
2. **Scheduler** ve el Pod pendiente → Decide en qué nodo colocarlo
3. **kubelet** (en el nodo asignado) → Crea y ejecuta el contenedor

### Proceso de programación (scheduling)

```
Pod creado
    ↓
API Server (etcd) - Estado deseado
    ↓
Scheduler evalúa:
  - Recursos disponibles en nodos
  - Restricciones (affinity, taints, tolerations)
  - Políticas de distribución
    ↓
Asigna Pod a un nodo específico
    ↓
kubelet en ese nodo crea el contenedor
```

### Factores que considera el Scheduler

1. **Recursos:** CPU y memoria disponibles en cada nodo
2. **Restricciones:** Affinity rules, taints/tolerations
3. **Políticas:** Distribución equilibrada de Pods
4. **Hardware:** Requisitos específicos (GPU, almacenamiento)

### Ver dónde está programado un Pod

```sh
# Ver en qué nodo está el Pod
kubectl get pods -o wide

# Salida muestra la columna NODE
NAME        READY   STATUS    RESTARTS   AGE   IP           NODE
nginx-pod   1/1     Running   0          5m    10.244.1.5   minikube
```

### Comandos relacionados

```sh
# Ver información del nodo donde está el Pod
kubectl describe pod <nombre-pod> | grep Node:

# Ver todos los nodos disponibles
kubectl get nodes

# Ver detalles de un nodo específico
kubectl describe node <nombre-nodo>
```

## Píldora 6: Imágenes de contenedores

### ¿Qué es una imagen?

Una **imagen de contenedor** es un paquete que contiene:
- La aplicación
- Sus dependencias
- El sistema operativo base
- Configuración

### ¿De dónde se descarga la imagen?

Las imágenes se descargan desde un **registro de contenedores** (container registry):

| Registro | URL | Ejemplo |
|----------|-----|---------|
| **Docker Hub** | `docker.io` (por defecto) | `nginx:latest` = `docker.io/library/nginx:latest` |
| **Google Container Registry** | `gcr.io` | `gcr.io/my-project/my-app:v1.0` |
| **Amazon ECR** | `<account>.dkr.ecr.<region>.amazonaws.com` | `123456789.dkr.ecr.us-east-1.amazonaws.com/my-app` |
| **Azure Container Registry** | `<registry>.azurecr.io` | `mi-registry.azurecr.io/my-app` |
| **GitHub Container Registry** | `ghcr.io` | `ghcr.io/usuario/repo:tag` |

### Cómo especificar la imagen en el Pod

```yaml
spec:
  containers:
    - name: nginx
      image: nginx:latest              # Docker Hub (por defecto)
      # image: docker.io/library/nginx:latest  # Forma completa
      # image: gcr.io/my-project/app:v1.0       # Google Container Registry
      # image: mi-registry.local:5000/app:tag   # Registro privado
```

### Proceso de descarga (Pull)

Cuando creas un Pod:

1. **kubelet** detecta que necesita la imagen
2. **containerd/Docker** intenta descargar la imagen
3. Si no está en caché local → Descarga desde el registro
4. Si está en caché → Usa la versión local

### Ver imágenes en Minikube

```sh
# Ver imágenes en caché de Minikube
minikube image ls

# Cargar una imagen local en Minikube
minikube image load mi-imagen:tag

# Construir imagen directamente en Minikube
minikube image build -t mi-imagen:tag .
```

### Imágenes privadas

Para usar imágenes privadas, necesitas crear un **Secret** con credenciales:

```sh
# Crear secret con credenciales de Docker Hub
kubectl create secret docker-registry regcred \
  --docker-server=docker.io \
  --docker-username=<usuario> \
  --docker-password=<password>

# Usar el secret en el Pod
```

```yaml
spec:
  imagePullSecrets:
    - name: regcred
  containers:
    - name: app
      image: usuario/private-image:tag
```

## Píldora 7: Crear y gestionar Pods

### Forma declarativa (manifiesto YAML)

**1. Crear el archivo `pod.yaml`:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80
```

**2. Aplicar el manifiesto:**

```sh
kubectl apply -f pod.yaml
```

### Forma imperativa (comando directo)

```sh
# Crear un Pod directamente
kubectl run nginx-pod --image=nginx:latest --port=80

# Con etiquetas
kubectl run nginx-pod --image=nginx:latest --port=80 -l app=nginx

# Con comando personalizado
kubectl run my-pod --image=busybox --command -- sleep 3600
```

### Comandos para gestionar Pods

| Comando | Qué hace |
|---------|----------|
| **`kubectl get pods`** | Lista todos los Pods |
| **`kubectl get pods -o wide`** | Lista con más información (IP, nodo) |
| **`kubectl describe pod <nombre>`** | Detalles completos del Pod |
| **`kubectl logs <nombre-pod>`** | Ver logs del Pod |
| **`kubectl logs -f <nombre-pod>`** | Logs en tiempo real |
| **`kubectl exec -it <nombre-pod> -- /bin/sh`** | Ejecutar comando en el Pod |
| **`kubectl delete pod <nombre>`** | Eliminar un Pod |
| **`kubectl delete -f pod.yaml`** | Eliminar Pod desde manifiesto |

### Ver todos los recursos (kubectl get all)

```sh
kubectl get all
```

**Salida típica:**

```
NAME            READY   STATUS    RESTARTS   AGE
pod/nginx-pod   1/1     Running   0          5m

NAME                 TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
service/kubernetes   ClusterIP   10.96.0.1       <none>        443/TCP   1d

NAME                    READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/nginx   1/1     1            1           5m

NAME                               DESIRED   CURRENT   READY   AGE
replicaset.apps/nginx-7c45b84548   1         1         1       5m
```

**Qué muestra `kubectl get all`:**

- **Pods:** Todos los Pods del namespace
- **Services:** Todos los servicios
- **Deployments:** Todos los deployments
- **ReplicaSets:** Todos los ReplicaSets

**Nota:** `get all` NO muestra todos los recursos. No incluye ConfigMaps, Secrets, Ingress, etc.

### Opciones útiles con get

```sh
# Ver Pods en todos los namespaces
kubectl get pods -A

# Ver Pods con etiqueta específica
kubectl get pods -l app=nginx

# Ver Pods en formato YAML
kubectl get pod nginx-pod -o yaml

# Ver Pods en formato JSON
kubectl get pod nginx-pod -o json

# Watch (actualización continua)
kubectl get pods -w
```

| **Pending** | El Pod ha sido aceptado pero los contenedores aún no se han creado. Puede estar esperando recursos o descargando imágenes. |
| **Running** | El Pod está en un nodo y todos los contenedores están ejecutándose. |
| **Succeeded** | Todos los contenedores terminaron exitosamente (para Pods que ejecutan tareas de una sola vez). |
| **Failed** | Al menos un contenedor falló (terminó con error o fue terminado por el sistema). |
| **Unknown** | El estado del Pod no se pudo obtener (problema de comunicación con el nodo). |

### Fases del ciclo de vida

```
1. Creación del Pod
   ↓
2. Pendiente (Pending) - Esperando ser programado
   ↓
3. Programado (Scheduled) - Asignado a un nodo
   ↓
4. Inicialización (Init Containers si existen)
   ↓
5. Creación de contenedores
   ↓
6. Descarga de imágenes (Pull Image)
   ↓
7. Inicio de contenedores
   ↓
8. Running / Succeeded / Failed
```

### Comandos para ver el estado

```sh
# Ver estado de los Pods
kubectl get pods

# Ver detalles del estado
kubectl describe pod <nombre-pod>

# Ver eventos relacionados con el Pod
kubectl get events --field-selector involvedObject.name=<nombre-pod>
```

### Condiciones del Pod

Los Pods tienen condiciones que indican su estado:

- **PodScheduled:** El Pod ha sido programado en un nodo
- **Initialized:** Los contenedores init han terminado
- **ContainersReady:** Todos los contenedores están listos
- **Ready:** El Pod está listo para recibir tráfico

```sh
# Ver condiciones de un Pod
kubectl get pod <nombre-pod> -o yaml | grep -A 10 conditions
```

## Píldora 4: Tipos de procesos y políticas de reinicio

### Tipos de procesos según duración

| Tipo | Descripción | Ejemplo | restartPolicy recomendada |
|------|-------------|---------|---------------------------|
| **Proceso de larga duración** | Servicios que deben estar siempre corriendo (web servers, APIs, bases de datos) | nginx, API REST | `Always` |
| **Tarea de una sola vez** | Scripts o trabajos que se ejecutan una vez y terminan | Migración de BD, backup | `Never` o `OnFailure` |
| **Tarea periódica** | Trabajos que se ejecutan en intervalos (usar CronJob) | Reportes diarios | `Never` |

### restartPolicy

Define qué hacer cuando un contenedor termina:

| Valor | Qué hace |
|-------|----------|
| **Always** | Siempre reinicia el contenedor si termina (por defecto). Ideal para servicios que deben estar siempre corriendo. |
| **OnFailure** | Solo reinicia si el contenedor termina con código de error (no 0). Útil para trabajos que pueden fallar. |
| **Never** | Nunca reinicia el contenedor. Útil para trabajos de una sola ejecución. |

### Ejemplos según el tipo de proceso

**1. Servicio web (siempre corriendo):**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-server
spec:
  containers:
    - name: nginx
      image: nginx:latest
  restartPolicy: Always    # Se reinicia automáticamente si falla
```

**2. Tarea de una sola vez (migración):**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: db-migration
spec:
  containers:
    - name: migrate
      image: myapp:migrate
      command: ["/bin/sh", "-c", "python migrate.py"]
  restartPolicy: Never     # No se reinicia, solo se ejecuta una vez
```

**3. Tarea que puede fallar (backup):**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: backup
spec:
  containers:
    - name: backup-script
      image: backup:latest
  restartPolicy: OnFailure  # Solo se reinicia si falla
```

### Nota importante sobre Pods

**Los Pods NO se auto-reparan si se eliminan.** Si un Pod se elimina (accidentalmente o por fallo del nodo), **no se recrea automáticamente** a menos que esté gestionado por un controlador como:

- **Deployment:** Mantiene Pods corriendo y los recrea si se eliminan
- **ReplicaSet:** Mantiene un número fijo de réplicas
- **StatefulSet:** Para aplicaciones con estado
- **DaemonSet:** Un Pod por nodo

**Por eso:** En producción, usa **Deployments** en lugar de Pods directos.

## Píldora 5: Kubernetes Scheduler

### ¿Qué es el Scheduler?

El **Kubernetes Scheduler** es un componente del plano de control que decide **en qué nodo** se ejecutará cada Pod.

### ¿Dónde se crea el Pod?

**El Pod NO se crea directamente en un nodo.** El proceso es:

1. **Usuario/Controlador** crea el Pod → Se guarda en el API Server
2. **Scheduler** ve el Pod pendiente → Decide en qué nodo colocarlo
3. **kubelet** (en el nodo asignado) → Crea y ejecuta el contenedor

### Proceso de programación (scheduling)

```
Pod creado
    ↓
API Server (etcd) - Estado deseado
    ↓
Scheduler evalúa:
  - Recursos disponibles en nodos
  - Restricciones (affinity, taints, tolerations)
  - Políticas de distribución
    ↓
Asigna Pod a un nodo específico
    ↓
kubelet en ese nodo crea el contenedor
```

### Factores que considera el Scheduler

1. **Recursos:** CPU y memoria disponibles en cada nodo
2. **Restricciones:** Affinity rules, taints/tolerations
3. **Políticas:** Distribución equilibrada de Pods
4. **Hardware:** Requisitos específicos (GPU, almacenamiento)

### Ver dónde está programado un Pod

```sh
# Ver en qué nodo está el Pod
kubectl get pods -o wide

# Salida muestra la columna NODE
NAME        READY   STATUS    RESTARTS   AGE   IP           NODE
nginx-pod   1/1     Running   0          5m    10.244.1.5   minikube
```

### Comandos relacionados

```sh
# Ver información del nodo donde está el Pod
kubectl describe pod <nombre-pod> | grep Node:

# Ver todos los nodos disponibles
kubectl get nodes

# Ver detalles de un nodo específico
kubectl describe node <nombre-nodo>
```

## Píldora 6: Imágenes de contenedores

### ¿Qué es una imagen?

Una **imagen de contenedor** es un paquete que contiene:
- La aplicación
- Sus dependencias
- El sistema operativo base
- Configuración

### ¿De dónde se descarga la imagen?

Las imágenes se descargan desde un **registro de contenedores** (container registry):

| Registro | URL | Ejemplo |
|----------|-----|---------|
| **Docker Hub** | `docker.io` (por defecto) | `nginx:latest` = `docker.io/library/nginx:latest` |
| **Google Container Registry** | `gcr.io` | `gcr.io/my-project/my-app:v1.0` |
| **Amazon ECR** | `<account>.dkr.ecr.<region>.amazonaws.com` | `123456789.dkr.ecr.us-east-1.amazonaws.com/my-app` |
| **Azure Container Registry** | `<registry>.azurecr.io` | `mi-registry.azurecr.io/my-app` |
| **GitHub Container Registry** | `ghcr.io` | `ghcr.io/usuario/repo:tag` |

### Cómo especificar la imagen en el Pod

```yaml
spec:
  containers:
    - name: nginx
      image: nginx:latest              # Docker Hub (por defecto)
      # image: docker.io/library/nginx:latest  # Forma completa
      # image: gcr.io/my-project/app:v1.0       # Google Container Registry
      # image: mi-registry.local:5000/app:tag   # Registro privado
```

### Proceso de descarga (Pull)

Cuando creas un Pod:

1. **kubelet** detecta que necesita la imagen
2. **containerd/Docker** intenta descargar la imagen
3. Si no está en caché local → Descarga desde el registro
4. Si está en caché → Usa la versión local

### Ver imágenes en Minikube

```sh
# Ver imágenes en caché de Minikube
minikube image ls

# Cargar una imagen local en Minikube
minikube image load mi-imagen:tag

# Construir imagen directamente en Minikube
minikube image build -t mi-imagen:tag .
```

### Imágenes privadas

Para usar imágenes privadas, necesitas crear un **Secret** con credenciales:

```sh
# Crear secret con credenciales de Docker Hub
kubectl create secret docker-registry regcred \
  --docker-server=docker.io \
  --docker-username=<usuario> \
  --docker-password=<password>

# Usar el secret en el Pod
```

```yaml
spec:
  imagePullSecrets:
    - name: regcred
  containers:
    - name: app
      image: usuario/private-image:tag
```

## Píldora 7: Crear y gestionar Pods

### Forma declarativa (manifiesto YAML)

**1. Crear el archivo `pod.yaml`:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80
```

**2. Aplicar el manifiesto:**

```sh
kubectl apply -f pod.yaml
```

### Forma imperativa (comando directo)

```sh
# Crear un Pod directamente
kubectl run nginx-pod --image=nginx:latest --port=80

# Con etiquetas
kubectl run nginx-pod --image=nginx:latest --port=80 -l app=nginx

# Con comando personalizado
kubectl run my-pod --image=busybox --command -- sleep 3600
```

### Comandos para gestionar Pods

| Comando | Qué hace |
|---------|----------|
| **`kubectl get pods`** | Lista todos los Pods |
| **`kubectl get pods -o wide`** | Lista con más información (IP, nodo) |
| **`kubectl describe pod <nombre>`** | Detalles completos del Pod |
| **`kubectl logs <nombre-pod>`** | Ver logs del Pod |
| **`kubectl logs -f <nombre-pod>`** | Logs en tiempo real |
| **`kubectl exec -it <nombre-pod> -- /bin/sh`** | Ejecutar comando en el Pod |
| **`kubectl delete pod <nombre>`** | Eliminar un Pod |
| **`kubectl delete -f pod.yaml`** | Eliminar Pod desde manifiesto |

### Ver todos los recursos (kubectl get all)

```sh
kubectl get all
```

**Salida típica:**

```
NAME            READY   STATUS    RESTARTS   AGE
pod/nginx-pod   1/1     Running   0          5m

NAME                 TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
service/kubernetes   ClusterIP   10.96.0.1       <none>        443/TCP   1d

NAME                    READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/nginx   1/1     1            1           5m

NAME                               DESIRED   CURRENT   READY   AGE
replicaset.apps/nginx-7c45b84548   1         1         1       5m
```

**Qué muestra `kubectl get all`:**

- **Pods:** Todos los Pods del namespace
- **Services:** Todos los servicios
- **Deployments:** Todos los deployments
- **ReplicaSets:** Todos los ReplicaSets

**Nota:** `get all` NO muestra todos los recursos. No incluye ConfigMaps, Secrets, Ingress, etc.

### Opciones útiles con get

```sh
# Ver Pods en todos los namespaces
kubectl get pods -A

# Ver Pods con etiqueta específica
kubectl get pods -l app=nginx

# Ver Pods en formato YAML
kubectl get pod nginx-pod -o yaml

# Ver Pods en formato JSON
kubectl get pod nginx-pod -o json

# Watch (actualización continua)
kubectl get pods -w
```

## Píldora 8: Ejemplos prácticos

### Ejemplo 1: Pod simple con nginx

**Archivo `nginx-pod.yaml`:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
    env: dev
spec:
  containers:
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80
          name: http
      resources:
        requests:
          memory: "128Mi"
          cpu: "100m"
        limits:
          memory: "256Mi"
          cpu: "200m"
  restartPolicy: Always
```

**Crear y verificar:**

```sh
# Crear el Pod
kubectl apply -f nginx-pod.yaml

# Ver el estado
kubectl get pods

# Ver detalles
kubectl describe pod nginx-pod

# Ver logs
kubectl logs nginx-pod

# Ver todos los recursos
kubectl get all
```

### Ejemplo 2: Pod con múltiples contenedores

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: multi-container-pod
spec:
  containers:
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80
    - name: log-sidecar
      image: busybox:latest
      command: ['sh', '-c', 'tail -f /var/log/nginx/access.log']
      volumeMounts:
        - name: logs
          mountPath: /var/log/nginx
  volumes:
    - name: logs
      emptyDir: {}
```

### Ejemplo 3: Pod con tarea de una sola vez

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: one-time-task

  containers:
    - name: task

      command: ['sh', '-c', 'echo "Tarea completada" && sleep 5']

```

**Ejecutar:**

```sh
kubectl apply -f one-time-task.yaml

# Ver el estado (debería pasar a Succeeded)
kubectl get pods

# Ver logs
kubectl logs one-time-task
```

### Ejemplo 4: Flujo completo - Crear, verificar, eliminar

```sh
# 1. Crear Pod desde manifiesto
kubectl apply -f nginx-pod.yaml

kubectl get pods
kubectl get pods -o wide

kubectl get all

# 7. Eliminar el Pod
kubectl delete pod nginx-pod

kubectl delete -f nginx-pod.yaml
```

## Resumen rápido

| Concepto | Punto clave |
|----------|-------------|
| **Pod vs Contenedor** | Pod = envoltorio de Kubernetes; Contenedor = proceso aislado |
| **Taxonomía** | apiVersion: v1, kind: Pod, metadata (name, labels), spec (containers, restartPolicy) |
| **Ciclo de vida** | Pending → Running → Succeeded/Failed |
| **Tipos de procesos** | Larga duración (Always), una vez (Never), puede fallar (OnFailure) |
| **Scheduler** | Decide en qué nodo se ejecuta el Pod |
| **Imágenes** | Se descargan de registros (Docker Hub por defecto) |
| **Crear Pod** | `kubectl apply -f pod.yaml` o `kubectl run` |
| **Ver recursos** | `kubectl get all` muestra Pods, Services, Deployments, ReplicaSets |
