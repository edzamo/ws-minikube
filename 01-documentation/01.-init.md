## Píldora 1: Iniciar Minikube con Kubernetes v1.32

Inicia el clúster local con la versión recomendada de Kubernetes:

```sh
minikube delete
minikube start --kubernetes-version=v1.32
```

**Si algo sale mal** (por ejemplo, errores al habilitar addons como `storage-provisioner`), repite estos mismos comandos para eliminar el clúster y recrearlo desde cero:

```sh
minikube delete
minikube start --kubernetes-version=v1.32
```

## Píldora 2: Configuración de Minikube

Minikube permite configurar opciones antes de iniciar el clúster. La configuración se guarda y se aplica automáticamente en futuros inicios.

### Flujo completo: Configurar y reiniciar el clúster

Este es el flujo recomendado cuando quieres cambiar la configuración o asegurarte de usar una versión específica de Kubernetes:

```sh
# 1. Ver la configuración actual
minikube config view

# 2. Eliminar el clúster existente (opcional, pero recomendado para aplicar cambios)
minikube delete

# 3. Configurar la versión de Kubernetes (opcional, también puedes usar --kubernetes-version directamente)
minikube config set kubernetes-version v1.32

# 4. Iniciar el clúster con la configuración establecida
minikube start --kubernetes-version=v1.32
```

### Comandos de configuración

| Comando | Qué hace |
|---------|----------|
| **`minikube config view`** | **Muestra** todas las opciones de configuración actuales de Minikube. Incluye driver, versión de Kubernetes, memoria, CPUs, etc. |
| **`minikube config set <clave> <valor>`** | **Establece** una opción de configuración. Ejemplo: `minikube config set kubernetes-version v1.32` |
| **`minikube config unset <clave>`** | **Elimina** una opción de configuración específica. |
| **`minikube config get <clave>`** | **Obtiene** el valor de una configuración específica. |

### Ejemplo de salida de `minikube config view`

```sh
minikube config view
```

**Salida esperada:**

```
- driver: docker
- kubernetes-version: v1.32.0
- memory: 2200
- cpus: 2
- disk-size: 20000mb
```

### Opciones de configuración comunes

Puedes configurar:

- **`kubernetes-version`**: Versión de Kubernetes a usar
- **`driver`**: Driver de virtualización (docker, virtualbox, kvm2, etc.)
- **`memory`**: Memoria RAM asignada al nodo (en MB)
- **`cpus`**: Número de CPUs asignadas
- **`disk-size`**: Tamaño del disco (ej: `20000mb`)

### Ejemplos prácticos

Configurar la versión de Kubernetes:

```sh
minikube config set kubernetes-version v1.32
```

Configurar memoria y CPUs:

```sh
minikube config set memory 4096
minikube config set cpus 4
```

Ver solo una configuración específica:

```sh
minikube config get kubernetes-version
```

Eliminar una configuración:

```sh
minikube config unset memory
```

### Relación con `minikube start`

Cuando ejecutas `minikube start`, Minikube usa:
1. Las configuraciones establecidas con `minikube config set`
2. Los parámetros pasados directamente en la línea de comandos (ej: `--kubernetes-version=v1.32`)

**Los parámetros de línea de comandos tienen prioridad** sobre las configuraciones guardadas.

**Nota:** Después de cambiar la configuración, es recomendable ejecutar `minikube delete` antes de `minikube start` para asegurar que los cambios se apliquen correctamente.

## Píldora 3: Múltiples clusters con perfiles

Los **perfiles** de Minikube permiten tener múltiples clústeres independientes en la misma máquina, cada uno con su propia configuración, versión de Kubernetes y recursos.

### ¿Por qué usar múltiples clusters?

- **Desarrollo y pruebas:** Un cluster para desarrollo y otro para pruebas
- **Diferentes versiones de Kubernetes:** Probar aplicaciones en distintas versiones
- **Aislamiento:** Separar proyectos o entornos completamente
- **Recursos diferentes:** Clusters con distintas configuraciones de CPU/memoria

### Comandos principales de perfiles

| Comando | Qué hace |
|---------|----------|
| **`minikube profile list`** | **Lista** todos los perfiles disponibles y muestra cuál está activo actualmente |
| **`minikube start -p <nombre>`** | **Crea e inicia** un nuevo cluster con el nombre de perfil especificado |
| **`minikube stop -p <nombre>`** | **Detiene** el cluster del perfil especificado |
| **`minikube delete -p <nombre>`** | **Elimina** el cluster del perfil especificado |
| **`minikube status -p <nombre>`** | **Muestra el estado** del cluster del perfil especificado |

### Crear y gestionar múltiples clusters

#### 1. Listar perfiles existentes

```sh
minikube profile list
```

**Salida esperada:**

```
|----------|-----------|----------------------|-------------------|
| Profile  | VM Driver |     Kubernetes       |      Status       |
|----------|-----------|----------------------|-------------------|
| minikube | docker    | v1.32.0              | Running           |
| cluster1 | docker    | v1.32.0              | Stopped           |
| cluster2 | docker    | v1.31.0              | Stopped           |
|----------|-----------|----------------------|-------------------|
```

#### 2. Crear un nuevo cluster con perfil

```sh
# Crear cluster1 con Kubernetes v1.32
minikube start -p cluster1 --kubernetes-version=v1.32

# Crear cluster2 con Kubernetes v1.31 y más recursos
minikube start -p cluster2 --kubernetes-version=v1.31 --memory=4096 --cpus=4

# Crear cluster de desarrollo con configuración específica
minikube start -p dev-cluster --kubernetes-version=v1.32 --driver=docker
```

#### 3. Detener un cluster específico

```sh
# Detener cluster1
minikube stop -p cluster1

# Detener el cluster por defecto (minikube)
minikube stop
```

#### 4. Eliminar un cluster

```sh
# Eliminar cluster1
minikube delete -p cluster1

# Eliminar el cluster por defecto
minikube delete
```

### Trabajar con kubectl en diferentes perfiles

Cuando tienes múltiples clusters, necesitas especificar con cuál trabajar.

#### Opción 1: Usar el flag `-p` con minikube kubectl

```sh
# Ejecutar kubectl en cluster1
minikube kubectl -- -p cluster1 get pods

# Ver nodos en cluster2
minikube kubectl -- -p cluster2 get nodes
```

#### Opción 2: Cambiar el contexto de kubectl

```sh
# Ver todos los contextos disponibles
kubectl config get-contexts

# Cambiar al contexto de cluster1
kubectl config use-context cluster1

# Ahora todos los comandos kubectl usan cluster1
kubectl get pods

# Cambiar al contexto de cluster2
kubectl config use-context cluster2
```

#### Opción 3: Crear alias para facilitar el uso

```sh
# Alias para cluster1
alias k1='minikube kubectl -- -p cluster1 --'

# Alias para cluster2
alias k2='minikube kubectl -- -p cluster2 --'

# Uso:
k1 get pods
k2 get nodes
```

### Comandos útiles con perfiles

#### Ver estado de un perfil específico

```sh
minikube status -p cluster1
```

#### Ver IP de un cluster específico

```sh
minikube ip -p cluster1
```

#### Abrir dashboard de un cluster específico

```sh
minikube dashboard -p cluster1
```

#### SSH a un cluster específico

```sh
minikube ssh -p cluster1
```

#### Ver configuración de un perfil

```sh
minikube config view -p cluster1
```

#### Configurar opciones de un perfil específico

```sh
# Configurar memoria para cluster1
minikube config set -p cluster1 memory 4096

# Configurar CPUs para cluster1
minikube config set -p cluster1 cpus 4
```

### Ejemplos prácticos de uso

#### Escenario 1: Desarrollo y producción local

```sh
# Cluster de desarrollo
minikube start -p dev --kubernetes-version=v1.32 --memory=2048 --cpus=2

# Cluster de producción (simulado)
minikube start -p prod --kubernetes-version=v1.32 --memory=4096 --cpus=4

# Trabajar en desarrollo
kubectl config use-context dev
kubectl apply -f app-dev.yaml

# Cambiar a producción
kubectl config use-context prod
kubectl apply -f app-prod.yaml
```

#### Escenario 2: Probar diferentes versiones de Kubernetes

```sh
# Cluster con Kubernetes 1.32
minikube start -p k8s-132 --kubernetes-version=v1.32

# Cluster con Kubernetes 1.31
minikube start -p k8s-131 --kubernetes-version=v1.31

# Probar aplicación en ambas versiones
minikube kubectl -- -p k8s-132 -- apply -f app.yaml
minikube kubectl -- -p k8s-131 -- apply -f app.yaml
```

#### Escenario 3: Múltiples proyectos aislados

```sh
# Proyecto A
minikube start -p proyecto-a --kubernetes-version=v1.32

# Proyecto B
minikube start -p proyecto-b --kubernetes-version=v1.32

# Usar alias para facilitar
alias ka='minikube kubectl -- -p proyecto-a --'
alias kb='minikube kubectl -- -p proyecto-b --'

# Trabajar en proyecto A
ka get all

# Trabajar en proyecto B
kb get all
```

### Gestión avanzada de perfiles

#### Ver todos los perfiles y sus detalles

```sh
# Listar perfiles
minikube profile list

# Ver información detallada de cada perfil
for profile in $(minikube profile list -o json | jq -r '.[] | select(.Name != "minikube") | .Name'); do
  echo "=== Perfil: $profile ==="
  minikube status -p $profile
  echo ""
done
```

#### Limpiar todos los perfiles detenidos

```sh
# Listar perfiles detenidos y eliminarlos
minikube profile list | grep Stopped | awk '{print $1}' | xargs -I {} minikube delete -p {}
```

#### Cambiar entre perfiles rápidamente

```sh
# Script para cambiar de perfil fácilmente
switch_cluster() {
  local profile=$1
  minikube stop 2>/dev/null
  minikube start -p $profile
  kubectl config use-context $profile
}

# Uso:
switch_cluster cluster1
```

### Notas importantes

1. **Recursos del sistema:** Cada cluster consume recursos. Asegúrate de tener suficiente RAM y CPU.

2. **Contexto activo:** Siempre verifica qué contexto está activo con `kubectl config current-context`.

3. **Puertos:** Si varios clusters están corriendo, pueden competir por puertos. Minikube maneja esto automáticamente.

4. **Configuración independiente:** Cada perfil tiene su propia configuración en `~/.minikube/profiles/<nombre>/`.

5. **Eliminación:** `minikube delete -p <nombre>` elimina solo ese cluster, no afecta a otros.

## Píldora 5: Directorio `~/.kube` y archivo de configuración

El directorio **`~/.kube`** (en Linux normalmente `/home/<usuario>/.kube`) es donde **kubectl** guarda la configuración para conectarse a uno o varios clústeres. Lo más importante es el archivo **`config`** (kubeconfig).

### Qué hace `cat config` (o `cat ~/.kube/config`)

Muestra el contenido del archivo de configuración de kubectl. **No modifica nada**; solo lo imprime en pantalla. Ese archivo define:

| Sección | Qué hace |
|--------|----------|
| **clusters** | Dónde está el API del clúster: URL del servidor (`server`) y certificado de la CA (`certificate-authority`) para confiar en la conexión (ej. Minikube en `https://192.168.49.2:8443`). |
| **contexts** | Combinan un clúster + un usuario + (opcional) un namespace. Indican “con qué clúster y con qué identidad” trabaja kubectl. |
| **users** | Credenciales para autenticarse: en Minikube son el **client-certificate** y la **client-key** (certificado y clave del usuario). |
| **current-context** | El contexto que está usando ahora kubectl (ej. `minikube`). |

En resumen: **`config`** le dice a kubectl a qué clúster conectarse, con qué certificados y qué contexto usar.

```sh
cat ~/.kube/config
```

## Píldora 6: Directorio `~/.minikube` y sus archivos

El directorio **`~/.minikube`** (normalmente `/home/<usuario>/.minikube`) contiene todos los archivos y datos que Minikube necesita para funcionar: certificados, configuración, caché, logs y máquinas virtuales.

### Estructura del directorio

| Archivo/Directorio | Qué hace y para qué sirve |
|-------------------|---------------------------|
| **`addons/`** | Directorio donde se almacenan los addons (complementos) de Minikube como `dashboard`, `ingress`, `storage-provisioner`, etc. |
| **`cache/`** | Almacena imágenes de contenedores y binarios descargados (ej. binarios de Kubernetes) para evitar descargas repetidas. |
| **`ca.crt`** | Certificado de la Autoridad Certificadora (CA) raíz de Minikube. Se usa para firmar otros certificados del clúster. |
| **`ca.key`** | Clave privada de la CA (solo lectura para el propietario). Se usa junto con `ca.crt` para generar certificados. |
| **`ca.pem`** | Certificado CA en formato PEM (equivalente a `ca.crt` pero en formato PEM). |
| **`cert.pem`** | Certificado en formato PEM usado para autenticación. |
| **`certs/`** | Directorio con certificados adicionales del clúster. |
| **`config/`** | Configuración específica de Minikube (diferente de `~/.kube/config`). |
| **`files/`** | Archivos varios que Minikube necesita copiar dentro de la máquina virtual. |
| **`key.pem`** | Clave privada en formato PEM (equivalente a `ca.key` pero en formato PEM). |
| **`last_update_check`** | Archivo que registra cuándo se verificó por última vez si hay actualizaciones de Minikube. |
| **`logs/`** | Directorio con logs de Minikube. Útil para depurar problemas. |
| **`machine_client.lock`** | Archivo de bloqueo para evitar que múltiples instancias de Minikube modifiquen el clúster simultáneamente. |
| **`machines/`** | Directorio con información sobre las máquinas virtuales creadas por Minikube (Docker, VirtualBox, etc.). |
| **`profiles/`** | Directorio con perfiles de Minikube. Cada perfil tiene su propia configuración y certificados (ej. `profiles/minikube/client.crt` y `client.key`). |
| **`proxy-client-ca.crt`** | Certificado CA del proxy cliente usado para autenticación del proxy. |
| **`proxy-client-ca.key`** | Clave privada del proxy cliente CA. |

### Comandos útiles

Ver el contenido del directorio:

```sh
ls -la ~/.minikube
# o desde dentro del directorio:
cd ~/.minikube && ll
```

Ver los logs si hay problemas:

```sh
cat ~/.minikube/logs/*.log
```

**Nota importante:** No modifiques manualmente estos archivos. Minikube los gestiona automáticamente. Si necesitas limpiar todo, usa `minikube delete`.

## Píldora 7: Addons de Minikube

Los **addons** son extensiones que añaden funcionalidades adicionales al clúster de Kubernetes en Minikube, facilitando tareas comunes como monitoreo, visualización, almacenamiento o gestión de tráfico.

### Comando para listar addons

```sh
minikube addons list
```

Este comando muestra todos los addons disponibles y su estado (habilitado ✅ o deshabilitado ❌).

**Ejemplo de salida:**

```
|----------------------|----------|--------------------------------|
|      ADDON NAME      | PROFILE  |           STATUS              |
|----------------------|----------|--------------------------------|
| dashboard            | minikube | enabled ✅                     |
| default-storageclass | minikube | enabled ✅                     |
| ingress              | minikube | disabled ❌                     |
| metrics-server       | minikube | disabled ❌                     |
| storage-provisioner  | minikube | enabled ✅                     |
|----------------------|----------|--------------------------------|
```

### Addons más importantes y comúnmente usados

| Addon | Qué hace y para qué sirve |
|-------|---------------------------|
| **`dashboard`** | Interfaz gráfica web para gestionar y visualizar el clúster. Permite ver pods, servicios, deployments, etc. desde el navegador. Se abre con `minikube dashboard`. |
| **`storage-provisioner`** | Provisión automática de volúmenes persistentes (PV). Permite crear PersistentVolumeClaims sin configurar manualmente el almacenamiento. **Esencial para aplicaciones que necesitan almacenamiento persistente.** |
| **`default-storageclass`** | Define la clase de almacenamiento por defecto del clúster. Permite que los PVCs se creen automáticamente sin especificar una StorageClass. |
| **`ingress`** | Permite gestionar reglas de entrada HTTP y HTTPS para exponer servicios externamente. Útil para routing y balanceo de carga. |
| **`metrics-server`** | Recolecta métricas de recursos (CPU, memoria) de los pods y nodos. Necesario para comandos como `kubectl top pods` y `kubectl top nodes`. |
| **`registry`** | Registro privado de imágenes Docker local. Permite hacer push/pull de imágenes sin usar registros externos como Docker Hub. |
| **`registry-creds`** | Carga credenciales de registros de contenedores (Docker Hub, GCR, ECR, etc.) para que los pods puedan hacer pull de imágenes privadas. |

### Comandos útiles para gestionar addons

Habilitar un addon:

```sh
minikube addons enable <nombre-del-addon>
# Ejemplo:
minikube addons enable ingress
```

Deshabilitar un addon:

```sh
minikube addons disable <nombre-del-addon>
# Ejemplo:
minikube addons disable ingress
```

Ver información detallada de un addon:

```sh
minikube addons describe <nombre-del-addon>
```

**Nota:** Algunos addons como `storage-provisioner` y `default-storageclass` suelen estar habilitados por defecto. Si encuentras errores al iniciar Minikube relacionados con addons, elimina y recrea el clúster.

## Píldora 8: Directorio `/etc/kubernetes` dentro del nodo

El directorio **`/etc/kubernetes`** está dentro del nodo de Minikube (no en tu máquina local). Contiene la configuración de los componentes del plano de control de Kubernetes que se ejecutan en el nodo.

### Cómo acceder al directorio

Primero, entra al nodo de Minikube con SSH:

```sh
minikube ssh
```

Una vez dentro del nodo, navega al directorio:

```sh
cd /etc/kubernetes
ls
```

### Contenido del directorio

| Archivo/Directorio | Qué hace y para qué sirve |
|-------------------|---------------------------|
| **`addons/`** | Directorio con los manifiestos YAML de los addons de Minikube instalados en el clúster (dashboard, ingress, storage-provisioner, etc.). |
| **`admin.conf`** | Archivo kubeconfig con credenciales de administrador. Permite que el usuario `admin` se conecte al API server de Kubernetes. |
| **`controller-manager.conf`** | Configuración para el **kube-controller-manager**, componente que ejecuta los controladores del clúster (replicas, endpoints, etc.). |
| **`kubelet.conf`** | Configuración del **kubelet**, agente que se ejecuta en cada nodo y gestiona los pods y contenedores. Es crítico para el funcionamiento del nodo. |
| **`manifests/`** | Directorio con los manifiestos estáticos de los componentes del plano de control (API server, etcd, scheduler, etc.). El kubelet lee estos archivos al iniciar. |
| **`scheduler.conf`** | Configuración del **kube-scheduler**, componente que decide en qué nodo se ejecuta cada pod. |
| **`super-admin.conf`** | Archivo kubeconfig con permisos de super administrador (máximos privilegios). Similar a `admin.conf` pero con acceso completo. |

### Comandos útiles

Ver el contenido del directorio desde fuera del nodo:

```sh
minikube ssh -- ls -la /etc/kubernetes
```

Ver el contenido de un archivo específico:

```sh
minikube ssh -- cat /etc/kubernetes/admin.conf
```

**Nota importante:** Estos archivos son parte del sistema interno de Kubernetes. No los modifiques manualmente a menos que sepas exactamente qué estás haciendo. Los cambios pueden romper el clúster.

## Píldora 9: Formas de crear recursos en Kubernetes

Hay dos formas principales: **declarativa** (archivos YAML) e **imperativa** (comandos directos).

### Forma declarativa

Se define el estado deseado en un archivo YAML y se aplica con `kubectl apply`. Recomendada para reproducibilidad y control.

**Ejemplo:** archivo `pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
    name: mi-pod
spec:
    containers:
        - name: nginx
          image: nginx:latest
```

Crear el recurso:

```sh
kubectl apply -f pod.yaml
```

### Forma imperativa

Se crean recursos desde la línea de comandos:

```sh
kubectl run mi-pod --image=nginx:latest
kubectl create deployment pruebas --image=nginx:latest --replicas=2
```

La forma declarativa facilita el versionado y la gestión de cambios.

## Píldora 10: Verbos principales de kubectl

Los comandos de `kubectl` siguen el patrón: **`kubectl <verbo> <recurso>`**. Los verbos son acciones que realizas sobre los recursos de Kubernetes.

### Estructura básica

```sh
kubectl <verbo> <tipo-de-recurso> [nombre-del-recurso]
```

**Ejemplo:**
```sh
kubectl get nodes
#     ↑    ↑
#  verbo  recurso
```

### Verbos principales y su función

| Verbo | Qué hace | Ejemplos |
|-------|----------|----------|
| **`get`** | **Lista o muestra** recursos. Es el verbo más usado para consultar el estado del clúster. | `kubectl get nodes`<br>`kubectl get pods`<br>`kubectl get services`<br>`kubectl get deployments` |
| **`describe`** | **Muestra información detallada** de un recurso específico. Incluye eventos, configuración y estado actual. | `kubectl describe pod mi-pod`<br>`kubectl describe node minikube`<br>`kubectl describe service mi-servicio` |
| **`create`** | **Crea un nuevo recurso** de forma imperativa (desde línea de comandos) o desde un archivo. | `kubectl create deployment nginx --image=nginx`<br>`kubectl create -f pod.yaml` |
| **`apply`** | **Aplica cambios** a recursos desde un archivo YAML. Crea el recurso si no existe o lo actualiza si ya existe. Es el verbo recomendado para gestión declarativa. | `kubectl apply -f deployment.yaml`<br>`kubectl apply -f .` (aplica todos los YAML del directorio) |
| **`delete`** | **Elimina recursos** del clúster. Puede eliminar por nombre, archivo o tipo. | `kubectl delete pod mi-pod`<br>`kubectl delete -f pod.yaml`<br>`kubectl delete deployment nginx` |
| **`edit`** | **Abre el recurso en un editor** para modificarlo directamente. Los cambios se aplican al guardar. | `kubectl edit pod mi-pod`<br>`kubectl edit deployment nginx` |
| **`logs`** | **Muestra los logs** de un pod o contenedor. Útil para depurar problemas. | `kubectl logs mi-pod`<br>`kubectl logs mi-pod -c nombre-contenedor`<br>`kubectl logs -f mi-pod` (seguimiento en tiempo real) |
| **`exec`** | **Ejecuta un comando** dentro de un contenedor en ejecución. Similar a `docker exec`. | `kubectl exec -it mi-pod -- /bin/bash`<br>`kubectl exec mi-pod -- ls /app` |
| **`port-forward`** | **Redirige el tráfico** de un puerto local a un pod o servicio en el clúster. Útil para acceder a servicios internos. | `kubectl port-forward pod/mi-pod 8080:80`<br>`kubectl port-forward service/mi-servicio 8080:80` |
| **`top`** | **Muestra métricas** de uso de recursos (CPU y memoria) de nodos o pods. Requiere `metrics-server` habilitado. | `kubectl top nodes`<br>`kubectl top pods`<br>`kubectl top pod mi-pod` |

### Recursos más comunes

Los recursos que puedes usar con estos verbos incluyen:

- **`pods`** (o `pod`) - Contenedores en ejecución
- **`nodes`** (o `node`) - Nodos del clúster
- **`services`** (o `svc`) - Servicios de red
- **`deployments`** (o `deploy`) - Deployments que gestionan pods
- **`replicasets`** (o `rs`) - ReplicaSets que mantienen réplicas de pods
- **`configmaps`** (o `cm`) - Configuraciones en forma de pares clave-valor
- **`secrets`** - Datos sensibles (contraseñas, tokens, etc.)
- **`namespaces`** (o `ns`) - Espacios de nombres que aíslan recursos

### Ejemplos prácticos

```sh
# Listar todos los nodos
kubectl get nodes

# Ver detalles de un nodo específico
kubectl describe node minikube

# Listar todos los pods
kubectl get pods

# Ver información detallada de un pod
kubectl describe pod mi-pod

# Ver logs de un pod en tiempo real
kubectl logs -f mi-pod

# Ejecutar un comando dentro de un pod
kubectl exec -it mi-pod -- /bin/sh

# Redirigir puerto local al pod
kubectl port-forward pod/mi-pod 8080:80
```

**Nota:** Muchos verbos aceptan la forma corta del recurso (ej. `pod` en lugar de `pods`, `svc` en lugar de `services`). Usa `kubectl api-resources` para ver todos los recursos disponibles.

## Píldora 11: Comandos útiles de kubectl

| Comando | Descripción |
|---------|-------------|
| `kubectl apply -f ejemplo.yml` | Aplica la configuración del archivo al clúster (crea o actualiza recursos). |
| `kubectl get all` | Lista pods, servicios, deployments, etc. en el namespace actual. |
| `kubectl delete -f ejemplo.yml` | Elimina los recursos definidos en el archivo. |
| `kubectl delete <tipo> <nombre>` | Elimina un recurso concreto (ej: `kubectl delete pod mi-pod`). |
| `kubectl delete all --all` | Elimina todos los recursos principales del namespace actual. |

### Ejemplos de eliminación

Eliminar un deployment creado de forma imperativa:

```sh
kubectl delete deployment pruebas
```

Eliminar todo en el namespace actual:

```sh
kubectl delete all --all
```

**Ejemplo de salida:**

```
pod "pod-hello-v2" deleted
service "mi-servicio" deleted
deployment.apps "mi-deployment" deleted
```

**Opciones útiles:**

- `-n <namespace>`: Ejecutar en un namespace concreto (ej: `kubectl delete all --all -n desarrollo`).
- `--grace-period=0 --force`: Eliminar sin esperar el período de gracia.
